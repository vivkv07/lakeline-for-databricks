How costs are calculated

This guide explains where each number in Lakeline for Databricks comes from. It covers what each number includes and excludes, and why the extension sometimes withholds a value instead of showing zero. All examples use made-up numbers. None of them come from a real workspace.

Estimated costs. Billing can be delayed; final invoices may differ.

Every amount in the extension is an estimate. The extension keeps different kinds of estimates apart and labels each one, so you can tell what you are looking at.

Local import file

A costs.json file is either an array of entries or {"entries": [...]}. It may be up to 5 MB and 5,000 entries. Each entry describes one resource for one period:

  • workspace: a workspace URL or numeric ID.
  • type: one of workspace, job, pipeline, warehouse, notebook or app. id must have the matching ID format.
  • periodDays (7, 30 or 90), currency (three letters), and total and previous (a number or null).
  • Optional: basis, owner, allocation, updatedAt (ISO timestamp), coverageEnd (YYYY-MM-DD), and daily as [{"date": "YYYY-MM-DD", "cost": number|null}].

The whole file is rejected with a list of problems if any entry is invalid. null stays missing and is never read as zero. Run and update rows aren't part of an import, so they show no amount. Imported figures are only as accurate as the file you provide.

Which workspace a page belongs to

Each workspace origin (for example https://<workspace>.cloud.databricks.com) has at most one cost connection. That connection is tied to a numeric workspace ID. The extension reads the ID from places it can trust, in this order:

  1. the o=, w= or workspace_id= URL parameters, including parameters inside supported hash routes;
  2. documented per-workspace host names, such as Azure adb-<id>.<n>.azuredatabricks.net;
  3. an ID the extension saw earlier in a tab on the same origin;
  4. the saved connection.

If no ID can be found, the banner shows Workspace ID not identified. If two sources disagree, it shows Conflicting workspace IDs in this URL. In both cases the extension doesn't guess. Every request from a page is checked against the saved workspace ID. A mismatch shows This page belongs to a different workspace. The extension never switches workspace or identity silently. If you have several workspaces open, you pick which one to connect.

SQL warehouse: Automatic or explicit

Under Connection preferences, the options page lists the SQL warehouses your identity can see, with name, ID, state and size. Pick one of two options:

  • Automatic prefers a usable warehouse that is already running. Among those, it prefers the smaller size (2X-Small first). Ties are broken by name, then ID. The choice is made when you save or reconnect, never per query, so your queries don't move between warehouses silently.
  • Explicit uses the warehouse you pick. If that warehouse is later deleted or you lose access, it is shown as unavailable rather than replaced.

A warehouse showing up in the list doesn't prove you have CAN USE on it or can read the billing tables. The first query reveals access problems, and the extension reports them specifically. See Permissions.

Cost queries run on your warehouse. The banner summary, badges, estimates and Explorer are ordinary SQL statements on the selected warehouse. They are billed like any other query. If the warehouse is stopped, the first query starts it, and it then runs until its own auto-stop. Choose a small warehouse that is usually running, or turn off Show costs inside Databricks when you don't need costs. The monitor widget never sends SQL in the background.

Usage and history sources

By default the extension reads system.billing.usage and system.query.history. You can instead name an approved view as a three-part name (catalog.schema.view) outside the system catalog. The view must expose the same columns as the system table it replaces. A source can't point at any other system table. Values are passed as SQL parameters, and names are validated and quoted, never pasted into SQL as free text.

Prices and how they are matched

Recorded cost is the signed sum of usage quantity multiplied by the matching unit price:

cost = SUM( usage_quantity × unit_price ) over every priced usage record in scope

Usage comes from system.billing.usage or your approved usage view. Prices come from exactly one of two price tables, chosen under Connection preferences. There is no free-text price table field, no schema override and no custom price view.

The two allowed price tables
Price tablePrice field readBasis labelNot included
system.billing.list_pricespricing.effective_list.defaultList pricePrivate or negotiated discounts. Cloud-provider charges.
system.billing.account_pricespricing.defaultAccount priceInvoice adjustments that aren't in that table. Cloud-provider charges.
  • The price field is decided from the table before any SQL is generated. The extension never reads both fields or falls back from one to the other.
  • There is no silent fallback between account and list prices, and totals never mix the two sources.
  • The basis (list or account) and the table name travel with every result, label, tooltip and CSV export.

account_prices may not exist for your account. On 2026-10-15, the official system-table reference documents list_prices but not account_prices. Third-party and community reports describe account_prices as a preview limited to some clouds and accounts, and in particular as unavailable on Azure. If your account doesn't have it, you see A required table is not available, and a step suggests switching to list_prices yourself. The extension never switches for you.

Matching rule

A usage record gets a unit price only when exactly one price row matches on every key below and that row's price is a number:

price.account_id    = usage.account_id
price.sku_name      = usage.sku_name
price.cloud         = usage.cloud
price.usage_unit    = usage.usage_unit
price.currency_code = :currency            -- the connection's currency, USD by default
usage.usage_end_time >= price.price_start_time
AND (price.price_end_time IS NULL OR usage.usage_end_time < price.price_end_time)
  • Half-open validity. A price is valid from its start time, inclusive, up to its end time, exclusive. A NULL end time means the price is still current.
  • No match means the record is unpriced.
  • Two or more matches (overlapping price rows) mean the record is ambiguous. It stays unpriced and is counted separately. It is never priced twice.
  • No currency conversion. The usage table has no currency column, so the currency comes from the matched price row. If your prices exist only in a currency other than the connection's, the records stay unpriced.
  • Native units. Quantities stay in their recorded unit (for example DBU). Nothing is converted.

Example (synthetic). A SKU has two list-price rows: $0.55 from 2026-01-01 00:00 UTC to 2026-08-01 00:00 UTC, and $0.50 from 2026-08-01 00:00 UTC with no end. A usage record ending exactly at 2026-08-01 00:00 UTC matches only the second row, so its price is $0.50. If someone added a third row covering the same time, the record would match two rows. It would become ambiguous and unpriced.

Signed corrections

Databricks corrects billing by adding records rather than editing old ones. A RETRACTION record has a negative quantity that cancels an ORIGINAL record. A RESTATEMENT record carries the corrected values. The extension keeps all three record types in the signed sum.

ORIGINAL +10 DBU RETRACTION −10 DBU RESTATEMENT +8 DBU → net 8 DBU

Corrections can arrive days after the original record. Past totals can therefore change, and a day or resource can legitimately show a negative amount. Negative amounts keep their minus sign.

Free usage: GENIE_FREE_USAGE

Databricks documents GENIE_FREE_USAGE as the SKU for free Genie usage. It is not billed and has no row in list_prices, and it appears in billing data from 20 July 2026. The extension prices this one SKU at zero. When the data has free quantity, the banner lists it separately as Free usage (not charged).

No other SKU is ever treated as free. A missing price is never assumed to be zero, and such records make the period a priced subtotal. A price row that really contains 0 is a real $0.

What is not included

  • Cloud-provider charges for classic compute, such as virtual machines, disks, network and storage. Your cloud provider bills these, and they don't appear in the price tables.
  • With list prices: private or negotiated discounts.
  • With account prices: invoice adjustments that aren't in the table.
  • Taxes, support plans, commitments and credits, and anything else outside the usage and price tables.

A priced subtotal is not necessarily a lower bound

Because corrections are signed, the missing records can be negative. Suppose the priced records sum to $40.00 and one unpriced record is a retraction of −10 DBU for a SKU with no matching price. The true total is below $40.00. Treat a priced subtotal as “the part that could be priced”, not as a minimum.

Change versus the prior period

The banner compares the amount shown for each period. That amount is the total when both periods are fully priced. It shows New spend when the prior amount is exactly zero, and No comparison when either period has no amount. If either period is only a priced subtotal, read the percentage with care.

Resource, title, run and update costs

  • Resource badges appear next to supported native names: jobs, pipelines, SQL warehouses, notebooks and Databricks Apps. Each shows that resource's recorded cost for the selected period.
  • Detail-page totals appear beside the job or pipeline title, for example Job total: $12.34 · 90d est. This is a period total, not lifetime spend.
  • Run and update rows show the recorded cost of that execution, not the resource's period total. Billing is searched across 365 UTC dates including today. The result can be incomplete when billing is delayed or when part of the execution falls outside that window. Amounts under $0.01 keep up to six decimal places, for example $0.000412.

How rows are identified

  • Identity comes only from real native links and IDs: job and run routes, pipeline and update routes, legacy routes, and supported notebook and app routes. Origin and workspace ID are validated. External, edit, create and navigation-only links are ignored.
  • The extension never infers an identity from a display name. It never reads the page's private application state.
  • On job run tables, a row can contain the current job's run link and also a different workflow in its Launched column. The badge uses the exact current job and run. It is never replaced by the launching workflow's whole cost.
  • Dense duration timeline bars and status dots stay native, without badges.
  • Requests are batched (at most 40 resources at a time) and de-duplicated. Badges follow scrolling, virtualized and recycled rows, route changes and period changes. Stale badges are removed.

Billing records name a notebook only for serverless notebook usage. Notebook badges therefore cover serverless notebook usage only. Usage on classic all-purpose clusters isn't split per notebook.

Jobs that trigger pipelines

Direct attribution uses billing records that carry the job's usage_metadata.job_id and, for a run, job_run_id. Databricks fills these for job compute and serverless jobs. It does not fill them for jobs that run on all-purpose compute.

A job task can start a pipeline update. That update is billed under the pipeline's dlt_pipeline_id and dlt_update_id, not the job's ID, so direct attribution alone misses it. The extension adds those updates as follows:

  1. Read system.lakeflow.pipeline_update_timeline for updates whose trigger is a job task. For those rows, trigger_details.job_task.job_id names the job and trigger_details.job_task.job_task_run_id names the task run.
  2. Join that task-run ID to system.lakeflow.job_task_run_timeline.run_id, limited to the same workspace and job. This gives each task run's parent job_run_id.
  3. De-duplicate. Timeline tables split long runs into hourly slices and can repeat task rows. The extension first reduces them to the unique set of pipeline updates for each job or run. It never joins raw timeline rows to billing, because that would multiply charges.
  4. Add the billing records of those updates to the direct records. Each billing record is counted at most once for the same job or run.
  • A job's period total includes every update the job triggered during the period.
  • A run's cost includes only the updates that map to exactly that parent run.

Example (synthetic). Run A of job 1111 has $3.10 of direct usage. Its second task triggered update U1 of pipeline P, which cost $1.25. Run A shows $4.35. Run B of the same job triggered nothing, so it shows only its direct cost. Pipeline P's own badge still shows all of P's cost, including U1. See why badges and the Explorer differ.

“Direct job cost” fallback

The Lakeflow timeline tables may be unreadable, or their schema may not match. In that case the extension still shows the direct amount, labeled Direct job cost, with a warning that triggered pipeline costs aren't included. This is not a complete job total. The status and warning are attached to each item, so one job's fallback doesn't relabel the others.

The extension never invents a share of a shared all-purpose cluster for a job. When billing records carry no job or run identity, that usage isn't attributed to the job.

Query History estimates

On the native SQL Query History page, each row can show an individual estimate, marked approx.. Generic warehouse-total badges are hidden on this page, and a short note near the page heading explains the estimates.

Matching a row to an execution

  • The extension prefers the statement ID from the row's native attributes or its execution-detail link.
  • Without a statement ID, it accepts only a unique metadata match on three things: warehouse ID, start time to the displayed second, and total duration within the display's rounding. Zero matches or several matches mean no estimate.
  • SQL text is never used for matching. The extension reads only statement IDs, timestamps, durations, status, cache flags and compute metadata. It never reads the SQL text or result rows of the queries it estimates.
  • Executions come from system.query.history (or your approved view) for the last 90 UTC dates, including today. Only executions on a supported SQL warehouse with a usable, completed execution time get a number.

Allocation method

  1. Find each execution's active window: active_start = MAX(query_start, query_end − execution_duration) and active_end = query_end. Time spent waiting or queued before execution is left out.
  2. Price the warehouse's recorded usage intervals that overlap those windows. Prices are matched exactly as described in Prices and matching.
  3. Include all executions visible to your identity that overlap those intervals, not only the rows on screen.
  4. Split each billing interval at every execution start and end. For each segment with at least one active execution, give each active execution an equal share:

    share = interval_cost × segment_duration ÷ interval_duration ÷ active_execution_count

  5. Add up each execution's shares. Segments with no active execution stay unallocated.

Assumptions

  • Cost is spread uniformly within each billing interval.
  • Concurrent queries share equally. CPU, memory or I/O use is not measured.
  • Active timing is approximate. Execution duration is reported by Databricks, and the active window is derived from it.
  • Executions you can't see, autoscaled clusters and unused capacity all affect the result.
  • Billing can be delayed or partial.
  • An estimate is not an invoice line. Estimates don't need to add up to the warehouse's bill.

Compute size previews

Next to supported native size options, the extension shows a prospective hourly cost labeled DBU only, for example ≈ $16.80/h per cluster · DBU only. It covers Databricks DBU charges only. It leaves out virtual machines, disks, network and other infrastructure. Rate unavailable is a normal state. The extension never saves or resizes compute while a preview is shown.

SQL warehouses

hourly preview = current DBU price of the warehouse's latest billed SKU × DBU per hour

  • The SKU is the warehouse's most recently billed DBU SKU in the last 90 UTC dates. Its price is the row in your selected price table that is valid right now. A warehouse with no billing in that window shows Rate unavailable. So does a warehouse whose selected type differs from its latest billed SKU.
  • While a warehouse is being created there is no warehouse ID yet. In that case only a serverless selection is priced, and only when the workspace billed exactly one serverless SQL SKU in the last 90 UTC dates.
  • The DBU per hour comes from the native page when the page shows it.
  • When the page doesn't show it, the extension uses the published Azure Databricks table below. It does so only for Azure serverless SQL warehouses. The table isn't applied on AWS or GCP, to classic or pro warehouses, or to real-time warehouses.
  • The rate is per cluster. With autoscaling, multiply by the number of running clusters. A Medium warehouse at 24 DBU/h and a synthetic $0.70 per DBU costs $16.80 per hour per cluster, so up to $50.40 per hour with a maximum of three clusters.

Interactive (all-purpose) compute

  • The extension uses current all-purpose DBU prices for the classic all-purpose SKUs seen in this workspace, or on the existing cluster, during the last 90 UTC dates. When Photon can be detected, it filters by Photon.
  • It needs exactly one unambiguous numeric rate. Otherwise it shows Rate unavailable.
  • That rate is multiplied by the DBU/h value or range the native page shows. The driver is included only where the native estimate includes it.
  • The preview updates when you change node type, worker range or other inputs.
  • An option is priced only if it shows DBU information. The extension never guesses DBU per core. It never uses SQL warehouse rates for interactive compute.

Example (synthetic). The native form shows 4–8 DBU/h and the matching rate is $0.55 per DBU. The preview reads ≈ $2.20–$4.40/h · DBU only.

Ownership: why the Explorer and native badges differ

In the Explorer, every billing record belongs to exactly one owner, chosen in this order of priority:

job → pipeline → warehouse → notebook → app → cluster → unattributed

This makes Explorer rows add up to the workspace total without double counting. Native badges answer a different question: what relates to this resource? A job badge can include pipeline updates the job triggered (see Jobs that trigger pipelines), while the Explorer assigns those records to the pipeline. In the earlier example, the Explorer counts update U1's $1.25 under pipeline P, while run A's badge also includes it. Both are correct for their purpose. Never add badge amounts together to get a workspace total.

Limits

  • The workspace summary query returns at most 20,000 rows.
  • Resource and run details load only when you ask for them. They are cached for about 5 minutes, and duplicate requests are merged.
  • Detail views list at most the top 200 ranked entities. The view shows the full number of candidates and says when the list is limited. The Runs view loads at most 500 runs for the period.
  • A result that is truncated, split into several chunks, or too large is rejected rather than shown as if complete.
  • Run durations are optional. If they can't be read, costs are still shown with a warning, and runs without a usable duration are left out of the scatter plot. A missing duration is never treated as zero.
  • A run's cost in the selected period is not its lifetime cost.

CSV export

Export writes the filtered table, together with its source, pricing basis and table, currency, UTC date bounds, freshness, scope and limit information. To keep spreadsheets safe, cells with quotes, commas or line breaks are quoted and escaped. Text cells that begin with =, +, -, @, a tab or a carriage return get a leading single quote, so spreadsheet apps don't run them as formulas. This also applies after leading spaces. Costs are written as plain numbers, so legitimate negative values stay numbers. Missing values are empty cells, never 0. Links are included only when they are validated native links. App names are validated, and routes are never guessed from IDs.

Heuristic flags

Flags point at numbers worth a second look. They are simple rules, not confirmed anomalies, and they don't explain causes.

Daily positive spike

  • Needs at least 14 fully priced days in the comparison period. If fewer exist, the flag is suppressed and the reason is shown.
  • Needs recent observed billing. If no billing was observed in the last 48 hours, the flag is suppressed, because recent days may still be incomplete.
  • Baseline samples are the previous period's days on the same weekday, if there are at least 3 of them. Otherwise all previous-period days are used.
  • A positive daily cost is flagged when it exceeds MAX(median × 1.5, median + 3 × MAD). MAD is the median absolute deviation from the median.

Example (synthetic). The same-weekday samples are $98, $100, $104 and $110. The median is $102. The deviations from it are 4, 2, 2 and 8, so the MAD is $3. The threshold is MAX($153, $111) = $153. A day at $160 is flagged, and a day at $140 is not.

High-cost runs

  • Needs at least 8 priced, completed runs with a positive observed duration in the same cohort, meaning runs of the same job.
  • A run is flagged when its cost exceeds Q3 + 1.5 × IQR, the upper quartile plus one and a half interquartile ranges. Quartiles are interpolated linearly between the closest ranks.

Example (synthetic). If the cohort's quartiles are Q1 = $2.00 and Q3 = $3.00, the IQR is $1.00 and runs above $4.50 are flagged.

Freshness

The banner shows a line such as Latest usage 10 h ago. This is the age of the newest usage_end_time among the billing records the summary read. Reporting periods end at 00:00 UTC today, so the smallest possible age is the time since midnight UTC.

  • Databricks documents that billing records are typically available within 12 hours, and that new workspaces can take longer. Early in the UTC day, yesterday may still be incomplete.
  • Freshness is a signal, not proof that every SKU is complete. Different products and SKUs can arrive at different times, and corrections can arrive days later.
  • No usage observed means the summary found no records. It doesn't mean zero spend.
  • Query history typically arrives within an hour, which is faster than billing. That is why recent queries often show Waiting for billing.

Caching and Refresh

  • Results are cached for about 5 minutes. Identical requests that are already running are merged instead of sent twice.
  • Cache entries are kept apart by workspace origin and ID, auth mode, price table, currency, connection revision, query kind, period and scope (resources, view or filter). Changing any of these makes a new request.
  • Refresh on the banner re-runs the workspace summary immediately. Badges and Query History estimates keep their own caches and expire on their own schedule.
  • Saving a connection or token clears the cache. A result that finishes after you changed the connection or settings is discarded rather than shown.
  • The cache lives in the extension's background memory. The browser can clear it sooner, for example when the background worker is suspended or the browser restarts.
  • Turning off Show costs inside Databricks pauses new cost requests from the page. Workspace colors stay active.

Missing data and status labels

Missing is not zero. Zero means the calculation produced zero. Missing means the extension couldn't calculate a value, because billing hasn't arrived, a price is missing, permission is lacking, or the data is outside the window. Showing missing values as $0 would understate spend, so the extension names the state instead.

What is stored where

  • Local storage (chrome.storage.local, kept until you remove the extension): settings, one connection per workspace origin (no secrets), workspace IDs seen in tabs, a validated import, the last 20 cleaned-up diagnostics, and workspace color preferences.
  • Session storage (chrome.storage.session, memory only): sign-in tokens, personal access tokens, the helper pairing, Genie conversations and the monitor's current state. These are cleared when the browser restarts or the extension is reloaded, updated or disabled. Content scripts can't read them.
  • The extension's own database (IndexedDB, on this device): only a personal access token you chose to Remember on this computer. Content scripts and web pages can't open it.
  • Signing in through the helper uses the Databricks CLI's own credential store. Those OAuth tokens never enter the extension.

Read-only Databricks access

  • SQL runs through the Statement Execution API. Only fixed, parameterized SELECT statements built by the extension are sent, chosen from a small set of named query kinds. The helper never runs SQL text sent by a caller. Long-running statements are cancelled.
  • Inventory and monitor calls are read-only GET requests from an allowlist: SQL warehouses, job runs, pipelines and clusters.
  • The extension never writes to Databricks. It never edits warehouses or clusters, and never starts or stops jobs.

Sign in with Databricks

The recommended way to connect, with no setup. On a workspace tab, open the extension and click Connect this workspace. Chrome asks once to allow access to that workspace and to localhost:8020. A tab opens on your workspace's own sign-in page and closes by itself once you are signed in. The extension then picks a SQL warehouse and list prices automatically, and costs show on the page.

It uses Databricks OAuth (authorization code with PKCE) against the workspace's own /oidc/v1/authorize and /oidc/v1/token endpoints, through Databricks' built-in public sign-in app (databricks-cli, the one the Databricks CLI uses). That app only returns to http://localhost:8020, so the extension reads the one-time code from its own sign-in tab; the code is useless without the PKCE secret the extension keeps. One all-apis sign-in covers cost queries, the run monitor and Genie. Tokens stay in browser session storage, refresh automatically, and are cleared when the browser closes or you disconnect the workspace.

If an admin turned off the built-in app, the popup says so: use a personal access token, or your organization's own app connection (below).

Optional: your organization's app connection

An account admin can register Lakeline once so the sign-in screen names your app and cost queries use a SQL-only sign-in (the run monitor and Genie then ask once more for all-apis):

  1. Open the account console, then Settings, App connections, Add connection.
  2. Name it, for example Lakeline. Add the redirect URL shown in the extension popup (it ends in .chromiumapp.org/ and is the same for everyone using this extension build).
  3. Choose the SQL and All APIs scopes. Leave client secret generation off; the extension is a public client.
  4. Copy the client ID and paste it in the popup once. New connections can take about 30 minutes to become active.

Admins who prefer the CLI can create the same public connection with databricks account custom-app-integration create --json '{"name":"Lakeline","redirect_urls":["<redirect URL from the popup>"],"scopes":["sql","all-apis","offline_access"]}' (no --confidential flag). The client ID is account-wide, so one registration covers every workspace in the account.

Other options remain under Connection preferences: a personal access token, or the local helper below.

Local helper troubleshooting

The local helper is a small Node program that listens only on 127.0.0.1:8766 and is never reachable from your network. It signs in with the Databricks CLI's browser OAuth and runs the same named cost queries as the extension, built from the same files. The CLI keeps its OAuth credentials in its own store. The helper holds only a short-lived access token in memory, sends it only to the selected workspace, and writes nothing to disk. These tokens never enter the extension. If you'd rather not run a helper, use a personal access token instead (below).

Start and pair

  1. You need Node.js 20 or newer and the Databricks CLI v1.12 or newer. Check the CLI version with databricks -v.
  2. Run the start script: start-helper.command on macOS (double-click), or start-helper.sh in a terminal on macOS or Linux. It checks for Node.js, starts the helper and opens the setup page, in Microsoft Edge if installed, otherwise in your default browser. If a helper of the same version is already running, the script reuses it and only reopens the setup page. If an older helper is running, the script tells you how to stop it.
  3. Select Connect workspace. The setup page passes a random 24-character pairing key to the extension in the URL fragment. The fragment is removed right away, and the key is never put in a query string, page HTML or logs. The extension checks the pairing with the helper before saving it, then opens Connection preferences.
  4. If automatic pairing fails, paste the key under Connection preferences. Manual entry is a fallback.

The pairing lives in session storage. After a browser restart or an extension reload, run the start script again, or reopen the setup page, to pair again. Reopening setup reuses a running helper of the same version. Each new helper start creates a new key, and the old pairing is dropped.

Dedicated CLI profiles

  • For cost queries, the helper uses a dedicated CLI profile named after the workspace you selected, dcc-<host>-<hash>, and requests the sql scope.
  • It never uses your DEFAULT profile or another existing profile.
  • It reuses a valid session. Otherwise it starts the browser sign-in, and you may see your company's SSO and a consent screen.
  • The monitor widget needs a separate one-time sign-in with the all-apis scope, on its own dcc-mon- profile. Cost queries keep the narrower sql scope.

Workspace colors

Workspace colors tint the Databricks top bar, and optionally the sidebar, so you can tell workspaces apart at a glance. Colors are independent of billing. They need no sign-in, helper or SQL, only site access for that workspace, which the extension requests when you save if it isn't already granted.

  • Open the popup and choose Workspace colors. Pick a saved workspace or enter a URL. Then choose a color with the picker, a six-digit hex value (#RRGGBB) or a preset. Check Also color the sidebar to tint the left navigation as well. Check the preview, then select Save.
  • Preferences are stored per origin|workspaceId, separately from cost connections. Changing or disconnecting billing never changes them.
  • A color saved for a URL without a workspace ID becomes a default for that host. A color for a specific workspace ID wins over the host default. If a page URL has no ID, the saved connection's ID is used when there is one.
  • Only the native top navigation is tinted, plus the sidebar and the frame around the page when you choose that option. The page itself, other headers and the extension's own banner aren't. Text switches to black or white based on contrast, and brand graphics and account initials are kept.
  • Controls that paint their own background, like the search box, pills, the New button and the selected sidebar item, take a lighter or darker shade of the same color, so the whole bar blends. Text on that shade stays at least as readable as on the bar itself.
  • Only strict #RRGGBB values are accepted. Nothing else you type reaches the injected styles.
  • Reset removes the override. If a host default still applies, the panel says so.
  • Colors stay on when cost display is paused.

Monitor widget

The monitor is a compact window that shows one workspace at a glance: active and recent job runs, pipeline updates, SQL warehouses and clusters. It is off until you turn on Monitor runs and compute in the popup. It is unavailable in Demo mode, which makes no Databricks requests.

  • What it polls. It polls every 60 seconds by default, or every 2 or 5 minutes if you choose. It uses only read-only REST GET requests: job runs (Jobs API 2.2), pipelines, SQL warehouses and clusters. These requests use no warehouse time. After errors it backs off, up to 30 minutes between attempts.
  • No background SQL. Background polling never sends SQL, so it never starts a stopped warehouse. The monitor's cost line uses the cached workspace summary when there is one. If loading costs would need a warehouse that isn't running, the monitor asks you first.
  • Sign-in. With the helper, the monitor needs a separate one-time sign-in. Select Sign in for monitor (broader access) in Connection preferences. It requests the all-apis scope on its own dcc-mon- profile. The helper forwards only an allowlist of read-only GET paths, and cost queries keep the SQL-only sign-in. In PAT mode, your token is used for both.
  • Toolbar badge. The extension icon shows the number of active runs. A different color plus “!” marks failures from the last 24 hours that the monitor window hasn't shown yet, so the alert doesn't rely on color alone.
  • Notifications. Desktop notifications for failed runs are opt-in (Desktop notification when a run fails). The browser asks for the notifications permission when you turn them on. You get at most one notification per run, and none for runs that failed before monitoring started. Your operating system's notification settings can still hide them.
  • Open the monitor when the browser starts is opt-in.
  • Monitor state is kept in memory-only session storage.

Float on top

The Float on top button tries to move the monitor into a Document Picture-in-Picture window, which stays above other windows while the browser runs. Limitations:

  • It needs Chrome or Edge 116 or newer and a click every time. It can't open automatically.
  • The floating window closes when the monitor window that opened it closes. The page can't choose where it appears.
  • Picture-in-Picture from an extension page hasn't been fully verified. If your browser refuses, keep using the normal monitor window.

Genie side panel

Select Ask Genie in the popup to open a side panel, pick a workspace and a Genie Agent (formerly a Genie space), and ask a question. You can close the panel and keep working: the extension's background sends the question, waits for Genie and keeps the answer until you come back. Genie decides how to answer and which SQL to run; Lakeline only carries the question and shows the result.

What is sent where

  • Only your question text, and only to your own workspace's Genie Conversation API under /api/2.0/genie/spaces.
  • Calls used: list agents, start a conversation, send a follow-up, read a message, read the query result, and re-run a result that expired. The extension's HTTP client allows exactly these paths for Genie, and nothing else; the local helper can't forward them.
  • No telemetry. Nothing goes to the extension's authors or any third party.

Sign-in and scopes

  • Sign in with Databricks. Every Genie API needs the genie scope, which all-apis includes. The default sign-in already grants all-apis. With your organization's own app connection, the panel asks once for it (Allow Genie and run status), the run monitor shares that consent, and cost queries keep the narrower sql scope.
  • Personal access token. The token is used. A token with limited scopes needs genie.
  • The local helper isn't supported for Genie. Demo mode shows synthetic agents and canned answers labeled DEMO, with no requests. Local import mode has no Genie.

Data handling

  • Answers can contain business data. Conversations are kept only in the browser's session storage: in memory, cleared when the browser closes, and not readable by scripts on web pages.
  • At most 8 conversations, 20 messages each and about 1.5 MB in total. Older result tables are dropped first, then older conversations. Clear now in the panel removes everything at once.
  • Conversations are never written to local storage, diagnostics, logs or notifications. The optional notification says only "Answer ready in" and the agent's name.
  • Everything is shown as plain text. Tables show up to 200 rows and 40 columns, with "showing N of M rows". The generated SQL stays behind Show SQL.

Polling, limits and cost

  • The panel and the background poll only while a question is in flight: after 1 second, then gradually less often, up to every 10 seconds (up to 60 seconds after errors). Lakeline stops waiting after 10 minutes, as Databricks recommends.
  • Up to three questions run at once, one per conversation. When Databricks reports a rate limit, the panel says so and never resends the question by itself.
  • If the browser restarts the extension's background mid-question, it picks the question up again within about 30 seconds.
  • Genie usage beyond a free monthly allowance is billed by Databricks, and the SQL it runs uses the agent's SQL warehouse, which starts if it is stopped.
  • The toolbar badge counts answers that arrived while the panel was closed, but only while the run monitor is off, because the monitor owns the badge.

Limitations

  • Estimates, not invoices. Amounts come from system tables and price tables, not from your bill.
  • No cloud-provider costs. Virtual machines, disks, network and storage billed by AWS, Azure or Google Cloud aren't included. Compute previews are DBU only.
  • Delayed billing. Recent days can be incomplete, and corrections can change past amounts.
  • account_prices availability. The table may be missing for your account or cloud. Azure in particular is reported to lack it. The extension never falls back to list prices for you.
  • Native page changes. Badges, previews and colors depend on the Databricks web interface. Selectors are best-effort and may need updates when Databricks changes its pages. When the extension can't find an element, it skips that element rather than guess.
  • Bounded history. Run search covers 365 UTC dates and query history 90 UTC dates. Older executions show no amount.
  • Visibility. Estimates and lists depend on what your identity can see.
  • Shared clusters. Usage on shared all-purpose clusters isn't split among jobs or notebooks.
  • Float on top may not work from extension pages. See Float on top.
  • Heuristic flags are simple rules, not anomaly detection.
